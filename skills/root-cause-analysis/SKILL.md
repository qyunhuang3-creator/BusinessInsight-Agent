# 业务异动归因

将问题转为可验证的比较。使用现有 inspect_data、run_sql 和 finish；根据 Observation 选择下一步，下面是分析检查点，不是固定 SQL 链。

1. **Data Quality Check**：检查时间范围、每日覆盖、首尾截断、内部断档、缺失、重复键与孤立记录。每日有记录只是可比较性代理，不能证明没有漏抽；保留不能确认的限制。
2. **Metric Definition**：固定时间归属、订单状态、金额组成、有效记录和分母口径。商品金额、运费、支付金额和净收入不可混用。AOV 的订单分母必须与金额范围一致。
3. **Trend Detection / MoM Analysis**：建立完整自然期间序列。仅比较相邻且均可比较的期间；零基期增长率不可计算。显著下降阈值须明确为分析规则，不能冒充统计显著性；同时按绝对变化排序，不预设异常期间。
4. **Metric Decomposition**：若金额 G=数量 V×单均金额 A，使用对称分解：数量贡献=(V1−V0)×(A1+A0)/2，单均金额贡献=(A1−A0)×(V1+V0)/2。验证贡献之和等于金额变化，考虑自然期间天数。
5. **Dimension Contribution**：各维度独立计算两期值、绝对变化、增长率、变化/总体变化。使用两期成员并集，保留新增、消失和 Unknown。总下降时增长组是抵消贡献；比例可超过百分之百。各组变化需对账总体，不跨维度相加。
6. **Drill Down**：根据已观测的下降集中度和业务解释价值选择维度及交叉维度。数量下降与单均金额下降需要不同的后续问题。说明为什么该 Observation 导致下一步选择，不机械重复错误或固定下钻顺序。
7. **Evidence / Hypothesis**：为事实引用成功 Tool Observation 的 action_id、字段和数值；必要时保留计算公式。流量、促销、供给、竞争等若无相应字段，只能写为待验证 Hypothesis，列出所需补充数据。
8. **Final Report**：说明可比较性、指标口径、候选期间、主期间选择、指标分解、各维度贡献、下钻、Evidence、Hypothesis、限制及未完成步骤。

## 粒度与 JOIN 安全

先明确每表一行代表什么，验证关联键是否唯一。订单、商品明细和支付记录不是同一粒度；禁止两个一对多表直接 JOIN 后累计金额。需要时先聚合至共同粒度；JOIN 前后对账行数与金额。不得用 SUM(DISTINCT 金额) 掩盖膨胀。SQL 保持只读，不因分析需要放松工具安全限制。

## Context 与停止条件

使用 compact schema、聚合结果及有来源的 findings，不读取原始大表到 Context。结果被截断时不能据此宣称完整排名。已有足够证据时 finish；达到轮次预算、API错误、无法确认覆盖或缺少必要数据时明确报告未完成与限制，不编造因果，不绕过既有重试策略。

## 使用边界

用于“为什么指标下降”“销售额为何异常”“找出指标变化原因”等归因请求。具体期间、SQL、维度顺序由当前问题和 Observation 决定。不得读取评测答案、评测报告或标准答案作为推理材料。
